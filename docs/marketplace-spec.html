1

Purpose & scope

DabApp currently lets a user publish a Listing (motorcycle, spare part or license plate) and negotiate its sale through Soom offers or an auction. There is no concept of a storefront, a cart, an order, or a seller wallet — a buyer cannot browse several sellers' catalogs, filter by vehicle compatibility, and check out. This document specifies the Marketplace module that adds that layer, reusing the existing catalog, payment and negotiation infrastructure wherever possible instead of duplicating it.

The scope covers backend (Laravel API), the buyer- and seller-facing mobile app, and the admin console. It excludes physical shipping/logistics integration, which is flagged as an open question in §8.

3

Functional requirements

Grouped by module. Each reflects both the approved UI reference (shop directory, vehicle-fit search, faceted filters, product detail with variants, tyre specs, reviews) and the transaction layer it currently lacks (cart, checkout, orders, wallet).

3.1Shops new

  • Become a seller — a user opens a shop from their profile (name, logo, banner, description, pickup location), mirroring the existing become-provider flow. Goes to pending until admin approval.
  • Shop directory — "All Shops" grid, searchable, sortable by rating / newest / most listings.
  • Shop page — banner, aggregate rating, all active listings, follow/favorite a shop.
  • Shop dashboard (seller side) — active listings, pending orders, wallet balance, review inbox.

3.2Catalog & vehicle-fitment search new

  • Browse entry points — Marketplace home with featured items, "All Accessories", "All Bike Types", "All Brands" shortcuts.
  • Search by vehicle — a guided Brand → Model → Year stepper that narrows results to parts confirmed compatible with the selected bike, reusing the existing motorcycle taxonomy.
  • Fitment badge — any product screen shows "Fits your bike" when the buyer has a garage vehicle saved (ties into the existing MyGarage model).

3.3Product & variants new

  • Product detail — description, image gallery, price, shop link, tabbed sections for Part Numbers and Size & Fit.
  • Variants — size / color / part-number combinations under one listing, each with its own stock and optional price delta.
  • Category-specific specs — e.g. tyres carry width, aspect ratio, rim diameter, load index and speed rating as a dedicated spec block and filter set.
  • Add to cart / Buy now — both actions available from the product page.

3.4Filters, sort & search new

  • Faceted filters — shop, price range, ship-from location, color, brand, size, rating; facets are configurable per category rather than hard-coded.
  • Sort — relevance, price asc/desc, rating, newest.
  • Empty / no-results states — distinct messaging for "nothing published yet" vs. "no match for current filters," with a one-tap filter reset.

3.5Reviews & ratings extend

  • Product reviews — star rating, text, optional photos, generalized from the existing Trainer/Route/POI review pattern.
  • Helpful vote and report review (flags suspected fake reviews for moderation, per the reference design).
  • Shop rating — rolls up from product reviews on that shop's listings.

3.6Cart, checkout & orders new

  • Cart — persists per user, supports mixed items from multiple shops, quantity edit, remove, live total.
  • Checkout — address / pickup point selection, payment method (saved card via existing BankCard, or PayTabs redirect), promo code (reuses PromoCode), order summary with commission-aware total.
  • Order splitting — one checkout can produce several Order records, one per shop, each with its own fulfillment status.
  • Order lifecycle — pending → paid → preparing → ready for pickup / shipped → completed → (cancelled / disputed), visible to both buyer and seller.
  • Order history — buyer order list with status and reorder; seller order queue with fulfillment actions.

3.7Payments, commission & wallet extend

  • Checkout payment — reuses PayTabs create/callback flow already wired for listing payments.
  • Commission — reuses CommissionSetting / PaymentSplit to take a marketplace cut per order line.
  • Seller wallet new — running balance credited on order completion, debited on payout request; payout request/approval flow mirrors the existing TrainerPayout admin pipeline.
  • Refunds new — full/partial refund tied to order cancellation or dispute resolution.

3.8Buyer–seller messaging extend

  • Generalizes the existing service chat-sessions into a per-order or per-listing conversation thread, so a buyer can ask a seller about fit or availability before purchasing.

3.9Notifications reuse

  • Order status changes, new message, review received, payout processed — all routed through the existing notification-token / template / preference system.

3.10Admin console extend

  • Shop moderation — approve/suspend shops, view shop-level metrics.
  • Category & facet configuration — define which filters/spec fields apply per category (e.g. tyre specs).
  • Order & dispute management — view all orders, intervene on disputes, trigger refunds.
  • Review moderation queue — act on reported/fake reviews.
  • Commission & payout management — reuses AdminCommissionController / AdminPayoutController patterns.

6

Non-functional requirements

  • Fitment lookup performance — composite index on (brand_id, model_id, year_id) in vehicle_fitments; the "search by vehicle" path must stay fast as catalog size grows.
  • Faceted filter performance — the current MySQL-only filtering may not scale once shop/price/color/size/rating facets combine; plan to introduce Meilisearch or Elasticsearch if P95 query time exceeds target once catalog volume is known.
  • Payment compliance — checkout money flow must stay inside PayTabs' supported capture model (see §8 on hold/escrow).
  • Media — product photos and review photos need consistent CDN-backed storage and size variants (thumbnail/full), consistent with existing ListingImage handling.
  • Concurrency — stock decrement on checkout must be race-safe across concurrent buyers for the same variant.

8

Risks & open questions

PayTabs escrow / hold-capture support unknown
If PayTabs cannot hold funds until order completion, the wallet must simulate escrow internally (credit only after buyer confirmation), adding backend complexity.
Fulfillment model undefined
Local pickup vs. carrier shipping changes the Order state machine and possibly requires a shipping-partner integration — needs a product decision before Phase 2 starts.
Fitment data quality
Vehicle-fitment search is only as good as the brand/model/year tagging on each listing; existing spare-part listings will need a backfill pass.
Review fraud workflow
The reference design includes "report a fake review" — the moderation SLA and enforcement action (hide vs. delete vs. warn seller) still need to be defined.
Search scale
Faceted filtering may outgrow plain MySQL queries; budget a follow-up spike for Meilisearch/Elasticsearch once real catalog volume is known.
